# MCP 2026-07-28 Migration Plan

Release candidate: https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/
Final spec: July 28, 2026
Current stable: 2025-11-25 (https://spec.modelcontextprotocol.io/specification/2025-11-25/)

## What Changes

### Stateless Core (breaking)

The handshake and session concept are gone. No `initialize`/`initialized` dance.
No session store, no MCP-Session-Id header, no sweeper, no tombstone.

Each POST /mcp is self-contained. The client includes protocol version and
capabilities on every request. The server includes its capabilities on every
response.

Impact on our transport (`streamable_http.clj`):
- Remove `create-session-store`, session atoms, `valid-session?`, `terminated-session?`,
  `touch-session!`, `delete-session!`, `prune-expired-sessions!`, `start-session-sweeper!`
- Remove MCP-Session-Id header handling in POST/DELETE/GET
- Remove DELETE /mcp entirely (no sessions to delete)
- Remove GET /mcp (SSE stream — no sessions means no SSE channel to attach)
- Simplify `handle-post` to a single-pass handler with no session branching
- The `dispatch-fn` signature changes from `(fn [msg sid] response)` to
  `(fn [msg] response)` — no session-id argument

New transport shape: one handler, no state. POST /mcp receives a request,
routes it through json-rpc, returns a response. Done.

New headers per spec:
- `Mcp-Method` — lets load balancers route by method (GET for idempotent tools)
- `Mcp-Cache-Ttl` — TTL hint for caching tools/list, resources/list, prompts/list

### Extensions Framework (additive)

Two new extension types:

**MCP Apps**: Server-rendered interactive UIs. The server sends UI components
(forms, tables, buttons) as part of the response. The client renders them.
This is a big addition — essentially a declarative UI protocol within MCP.
No immediate action; we'd spec `apps/list` and `apps/get` as new method
handlers when we're ready to support it.

**Tasks**: Long-running async operations. This is hook's lifecycle mapped to
MCP. Submit a task, poll for status, stream results. The protocol gets:
- `tasks/submit` — create a task
- `tasks/cancel` — cancel a task
- `tasks/get` — poll task status
- Notifications for status changes

This is directly relevant to hook. The pattern (submit → job id → poll → logs)
maps 1:1. When we implement Tasks, hook's supervisor and jobs registry are
the backend; we just add MCP method handlers on top.

### Authorization (additive, optional)

The spec aligns with OAuth 2.0 / OpenID Connect:
- Authorization metadata exchanged during handshake (well, the stateless equivalent)
- Token-based auth as the default
- Our existing Bearer token check in hook is compatible; no action needed unless
  we want full OAuth flow support

### Deprecations (informational)

- **Roots**: Client tells server about its filesystem roots. Deprecated.
  We never relied on it.
- **Sampling**: Server asks client to call an LLM. Deprecated.
  We never relied on it.
- **Logging**: Server pushes log messages to the client. Deprecated.
  We have `notify-log` in server.cljc. Remove when we drop support for 2025-11-25.

### JSON Schema 2020-12 (additive)

Tool `inputSchema` graduates from a restricted subset to full JSON Schema
2020-12. This means richer validation: `if/then/else`, `const`,
`$defs` references, etc. No code change on our side — we pass the schema
through to the MCP client. Clients are responsible for validation.

## Migration Strategy

### Phase 1: Spec Stabilization (July 28 — wait)

Don't touch anything until the final spec ships. The RC may change before
final. Watch the blog and spec repo. Tag the pre-migration state as `v0.3.0`.

### Phase 2: Session Erasure

Create a new transport file (e.g., `streamable_http_stateless.clj`) that
implements the 2026-07-28 transport from scratch. No shared code with the
old transport — the session logic is too deeply interwoven. Keep the old
transport around for backward compatibility.

#### Option B: Transport-Level InitializeResult

Consider making the transport intercept the `initialize` method automatically.
The transport would build the InitializeResult from `:server-info` and
`:capabilities` options passed to `run-server`, and only pass non-initialize
messages to the user's dispatch function.

Pros:
- Downstream servers never touch initialize response schema (eliminates
  `serverName` vs `serverInfo` bugs entirely)
- Natural fit for stateless spec where every request carries capabilities
- Single place to validate the spec-compliant shape

Cons:
- Couples transport to MCP lifecycle semantics (currently transport is
  content-agnostic)
- Adds complexity to `run-server` options
- Two code paths (intercept vs pass-through) for initialize
- The full handler stack already builds the correct InitializeResult;
  this only helps the case-dispatch pattern

Recommendation: make this optional. The transport checks if `:server-info`
is set in `run-server` opts. If set, intercept initialize. If not, pass
through to dispatch-fn as today. This preserves backward compatibility
and lets users opt in as they migrate to the stateless spec.

### Phase 3: Handler Simplification

The handler layer also changes. The pre-init/post-init state machine goes
away. The `handler-by-method` map is set once at session creation and never
changes. Remove `initialized-notification-handler`, the two-phase dispatch,
and the `:initialized` flag from session state.

### Phase 4: Tasks Extension

Add `tasks/submit`, `tasks/cancel`, `tasks/get` handlers. Wire hook's
supervisor (`hook.jobs`, `hook.supervisor`) behind them. This is where
hook-as-MCP-server comes together: POST /run → tasks/submit, job ID → task
ID, status stream → notifications.

### Phase 5: Drop 2025-11-25

Once nothing depends on the old transport, delete the session-based code.
Tag `v1.0.0`.
